# Code Review

1. High: `interceptor/executeChain` passthrough only runs against the first interceptor client, so the transparent proxy stops behaving like the same multi-hop chain used for normal proxied requests. In `csharp/sdk/src/ModelContextProtocol.Interceptors/Gateway/McpInterceptorGateway.cs:494-539`, `HandleInterceptorPassthrough` hard-codes `_options.InterceptorClients[0]` for `InterceptorRequestMethods.InterceptorExecuteChain`. That means a caller asking the proxy to execute the chain directly will never hit interceptors hosted on later clients, even though `InterceptorChainRunner` does run all configured clients sequentially for proxied MCP operations. This creates inconsistent behavior between `tools/*` through the gateway and `interceptor/executeChain` through the same gateway, and will silently skip validation/mutation layers in multi-interceptor deployments.

2. High: the proxy advertises `SupportedEvents = ["*"]` even when the configured interceptor servers only support a subset of events. In `csharp/sdk/src/ModelContextProtocol.Interceptors/Gateway/McpInterceptorGateway.cs:414-429`, the code ignores each interceptor server's advertised `capabilities.extensions.interceptors` and publishes a wildcard capability instead. Clients will reasonably take that as permission to invoke interception flows for any event through the proxy, but those requests can then fail downstream because no backing interceptor supports them. This is especially problematic for convenience/discovery scenarios, because the proxy is now overstating the remote contract it exposes.

3. Medium: `interceptor/invoke` passthrough treats every `McpException` as "not found", which masks real interceptor failures on earlier clients. In `csharp/sdk/src/ModelContextProtocol.Interceptors/Gateway/McpInterceptorGateway.cs:506-517`, the loop catches `McpException` broadly and continues to the next client. `InvokeInterceptorAsync` also throws `McpProtocolException` for real remote execution failures, timeouts, or invalid requests, not just missing interceptor names. With the current logic, if the first server finds the interceptor but its execution fails, the proxy will either invoke a different interceptor with the same name on a later server or incorrectly return "Interceptor '<name>' not found on any interceptor server". That loses the original error and can change which interceptor actually runs.

4. Medium: request-phase mutations for `resources/subscribe` are computed and then discarded before the backend call. In `csharp/sdk/src/ModelContextProtocol.Interceptors/Gateway/McpInterceptorGateway.cs:304-317`, the handler serializes `request.Params`, runs `_chainRunner.RunChainPhaseAsync(...)`, ignores the returned payload, and always forwards `request.Params!` to `backend.SubscribeToResourceAsync`. That makes validation-only interceptors work, but any mutation interceptor for `resources/subscribe` is ineffective in the transparent proxy path.

5. Medium: the new builder extension does not wire notification forwarding, so DI-based `WithInterceptorGateway(...)` setups miss one of the gateway's documented responsibilities. `csharp/sdk/src/ModelContextProtocol.Interceptors/Gateway/McpInterceptorGatewayBuilderExtensions.cs:20-48` only registers an `IConfigureOptions<McpServerOptions>`, while `McpInterceptorGateway`'s XML docs and sample both require a separate `RegisterNotificationForwarding(...)` call after the `McpServer` exists. Consumers using the convenience API will assume the builder-based setup is complete, but backend `tools/list_changed`, `prompts/list_changed`, and `resources/list_changed` notifications will never be forwarded unless they discover and invoke the gateway manually later.

Residual risk: the current gateway tests pass, but they only exercise a single interceptor client and mostly tools flows, so they do not cover the multi-client passthrough, advertised capability accuracy, or `resources/subscribe` mutation path described above.
